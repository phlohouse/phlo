The lab begins with gzip-compressed newline-delimited JSON files. Each line represents a sensor reading. stage_inbound() copies the selected scenario into generated-data/inbound/, the directory the Dagster worker actually reads.

read_batches(partition_date) sorts the delivery files, selects names ending in -{partition_date}.ndjson.gz, decodes their rows and concatenates them into a DataFrame. An empty selection raises FileNotFoundError. The source reader therefore has a concrete selection rule, rather than scanning every fixture for every run.

batch_id      b-1001
sensor_id     s-001
reading_value required float
recorded_at   event timestamp
batch_date    partition timestamp
quality_flag  ok | suspect

Partitioning divides work and data into identifiable slices. Here a requested date selects source files, and batch_date becomes an Iceberg identity partition. It is distinct from recorded_at, which describes when the measurement happened. A record can belong to a delivery partition yet have a stale event timestamp.

The clean fixture contains 12 rows across four sensors. The staged directory must be shared with the worker. Changing an environment variable only in the launching shell cannot select data inside another process.

02 Launch identity and an isolated catalog branch

Input
Asset name, partition date and current main catalog reference.
Output
An isolated run branch, logical Phlo run ID, Dagster run ID and recorded starting hash.
Launch correlation
The scenario must receive a logical run ID and find that exact run’s terminal report. A missing or unfinished report fails the scenario after its timeout.

The runner launches the ingestion asset through phlo materialize. An asset identifies the work that produces a dataset. A run identifies one execution. WAP gives that execution a branch named pipeline-run-<id>, starting from a recorded catalog state.

Nessie supplies versioned catalog references. A branch isolates changes to table metadata while main remains the reference used for published data. This is a catalog operation, not a Git branch in the source repository.

The launch carries both a logical Phlo run identity and a Dagster execution identity. They have different jobs. Phlo uses the logical ID to correlate evidence and the report returned for the launch. Dagster uses its ID to track execution. The runner polls the exact logical ID returned by the command, so an earlier successful report cannot satisfy a later launch.

03 Source execution, retries and Parquet staging

Input
The selected source files, run identity and retry policy.
Output
Normalized Parquet with Phlo metadata, plus an inventory of the staged objects.
Source execution
The injected error fails the first source attempt before it yields data. The second attempt succeeds. Exhausted retries would fail the run, not publish a partial success.

The strict source first calls its transient-failure hook, then returns a dlt.resource built from the selected records. dlt extracts and normalizes the records into staged Parquet. Phlo adds its metadata columns before inventorying those artifacts.

Staging makes the material being validated and loaded inspectable. The executor records object identities, byte counts and available record counts immediately before validation and writing. That ordering matters: recording the inventory before metadata injection would describe a different artifact from the one actually loaded.

In the retry scenario, a durable counter records attempt one and the injected fault raises before the source yields data. The Dagster retry policy permits another attempt, with a five-second delay and up to three retries on the strict asset. Attempt two succeeds.

attempts_recorded: 2
rows_added:        10
classification:   promoted

Retry safety has a boundary. Both assets use append writes. A declared unique_key="batch_id" does not turn an append into a deduplicating upsert. This pre-yield fault proves recovery before a write, not idempotent replay after a committed write.

Input
Staged Parquet rows and the asset’s contract/check configuration.
Output
Validation results; either permission to continue or an exception before the Iceberg write.
Data validation
Strict failures stop here, before the table-store write. Relaxed failures become warning evidence and allow execution to continue.

The executor evaluates the Pandera contract against the staged Parquet files. Required readings must be non-null and between −50 and 150. Identifier formats, temporal fields and the allowed quality_flag values form the rest of the physical contract. The optional score accepts NULL or a value from 0 to 100.

It then evaluates the configured domain checks. The strict asset attaches assert_batch_ids_unique. The relaxed asset attaches assert_recordings_near_partition, which rejects timestamps outside a seven-day window. These are distinct asset configurations, not one identical check suite.

With strict_validation=True, a failed contract or domain check raises before merge_to_table_store(). With relaxed validation, evaluation results remain available as warning evidence and execution can continue to the write.

strict + failed check → raise before write
relaxed + warning    → record result, continue
clean checks         → continue

The live strict scenario used one null reading. Dagster failed, main's hash and row count stayed unchanged, and the WAP branch remained. The duplicate-ID fixture was also checked in deterministic tests. The live warning fixture used seven records that were 23 days stale.

Input
Accepted staged Parquet, append configuration and the isolated branch reference.
Output
A candidate Iceberg table snapshot on the run branch, with before/after table evidence.
Write readback
Missing state or contradictory readback marks output evidence incomplete. A candidate snapshot here is still not publication on main.

After staged validation, merge_to_table_store() writes using merge_strategy="append" and the run's branch reference. MinIO stores the physical objects. Iceberg metadata identifies the files belonging to each table snapshot. Nessie identifies the catalog state through which those tables are resolved.

These are separate layers: an uploaded object is not a table snapshot, and a new snapshot on a run branch is not yet published on main. The executor reads table state before and after the write, then records snapshot IDs, schema hashes and observed row metrics. Missing or contradictory readback reduces the completeness of the evidence.

Schema evolution also needs precise evidence. The lab's score column is optional from the contract's initial definition. In the actual schema scenario, the column count was 13 both before and after. Eight new rows supplied scores and all 22 older rows retained NULL scores.

columns_before / after: 13 / 13
new_partition_rows:      8
old_rows_with_null_score:22 of 22

This proves preservation of old rows and ingestion of new optional values. It does not demonstrate adding a previously absent column through a live DDL migration.

06 Publication has its own evidence gate

Warning example: the reading is 23 days old

batch_idrecorded_atbatch_date
b-80012026-08-01T08:57:00Z2026-08-24T00:00:00Z
2026-08-24 − 2026-08-01 = 23 calendar days
Allowed lag: 0–7 days
Timeliness check: FAIL
Relaxed policy: warning, publication allowed
Output: 7 rows added to sensor_batches_relaxed on main

The row stays unchanged: publication does not repair its timestamp. The warning records why it missed the expectation.

Input
Dagster run outcome and quality evidence for the exact logical run.
Output
A publication decision: eligible to merge, blocked, or failed.
Publication gate
A failed run, blocking quality error or unavailable required quality evidence prevents promotion. Warning-only evidence permits promotion.

A successful ingestion execution leaves changes on its isolated branch. The WAP promotion sensor separately decides whether they can reach main. It consults the run outcome and durable quality evidence, rather than equating a successful process exit with a publication decision.

Write-Audit-Publish separates producing candidate data from exposing it to consumers. The audit boundary includes publication policy. Blocking quality errors prevent promotion. Missing required quality evidence also blocks promotion. Warning-only evidence remains non-blocking under the configured severity contract.

Failed Dagster runs must reach a terminal failed report and retain their branches. Successful relaxed runs can proceed with a quality aggregate of passed_with_warnings. The failed check remains in the evidence, so the reason for accepting imperfect data stays inspectable.

execution success ≠ publication success
blocking error    → no promotion
evidence missing  → no promotion
warning only      → promotion permitted

The warning scenario published seven rows to sensor_batches_relaxed on main. It did not add them to the strict sensor_batches table used by the example's dbt summary.

07 Merge intent, acknowledgement and uncertainty

Input
An eligible candidate branch, main’s current hash and a durable merge-intent record.
Output
A merged receipt, a known failed-merge record, or an unresolved outcome with the source retained.
Catalog merge
A rejected merge records merge_failed. An unacknowledged outcome stays uncertain. Neither authorizes branch cleanup.

Before calling the catalog, the sensor persists merge_state="merge_started" together with the source and target hashes. This is a durable record of intent across a process or network boundary. If recording intent fails, it does not perform the merge.

If the catalog reports failure, the sensor writes promotion_failed and merge_failed. A successful acknowledgement permits it to record merge_state="merged". That receipt is what lets a later sensor evaluation resume evidence finalization and cleanup without issuing the same merge again.

A crash can leave only merge_started. The merge may have committed and lost its acknowledgement, or may never have committed. Recovery keeps the branch and marks the outcome unknown. A moving target hash cannot resolve that uncertainty because another writer may have changed main.

merge_started → intent, outcome uncertain
merge_failed  → known failure, retain source
merged        → acknowledged success receipt

The regression added an unrelated main commit after a failed merge. The source branch and its data survived. The result recorded branch_retained=true and unchanged main rows for the failed batch.

Concurrent row accounting
The scenario fails if a successful batch contributes the wrong rows, a failed batch contributes rows, or required recovery state disappears.

The concurrency scenario stages two disjoint batches and submits both runs before polling their reports. The launches use different branches and share the same starting main ancestry. This exercises overlapping work, without assuming a particular worker scheduling order.

Optimistic concurrency checks that a change can still apply to the target state. Disjoint batch IDs do not guarantee that two updates to the same table metadata will merge cleanly. A conflict is acceptable if the published rows remain correct and the unsuccessful writer retains its recovery state.

In the recorded run, the classifications were promoted and blocked, and main gained 12 rows. The runner's blocked category includes a promotion_failed report. It checks exact row accounting and branch lifecycle for each result, rather than requiring both writers to succeed.

The fresh-catalog path is another concurrency boundary. The Nessie fallback only assigns the source when the target still matches the server's noAncestorHash. The conditional update prevents initialization from overwriting a concurrent writer.

The live concurrency test and the fresh-catalog happy path passed. Retained branches are recovery material, not proof that an automatic conflict-resolution strategy has completed.

09 Published state, cleanup and durable provenance

Input
A durable merged receipt and the run’s resource, quality and catalog evidence.
Output
A promoted WAP report, confirmed branch cleanup and exported ingestion evidence; rows visible on main.
Publication verification
The happy-path assertions require exactly 12 added rows, a changed main hash, no remaining promoted branch and all required evidence categories.

After a durable merged receipt, the sensor can clean up the owned run branch and finalize promotion. If a previous attempt already deleted the branch, recovery treats its absence as successful cleanup. An ambiguous merge intent must not authorize deletion.

Provenance connects a result to the inputs, artifacts and decisions that produced it. The happy path exports the ingestion report for the exact logical run and requires input, staged, output, lineage, artifact, snapshot, quality and catalog evidence. These requirements go beyond finding a green status label.

The live topology used SQLite for host Dagster's event storage and PostgreSQL for Phlo evidence. An event storage ID is only meaningful in its run/store context. Correlation must preserve that context, and the Dagster adapter must route the logical Phlo ID to the evidence store.
