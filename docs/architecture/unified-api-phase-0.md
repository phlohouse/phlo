# Unified API contract and route inventory (issue #1035, phase 0)

This document records the **phase-0 inventory and planned** `/api/v1` behavior as it stood before implementation. Phase 1 mounts `/api/v1/me`, `/api/v1/environments`, `/api/v1/services`, and `/api/v1/events`; their current behavior is in the [phase-1 reference](../reference/unified-api-phase-1.md). The 107 legacy application endpoints below were inventoried from `phlo_api.main:app` by `scripts/generate_reference_docs.py`. The current [generated inventory](../reference/http-api.md) also includes the new v1 routes. It omits FastAPI's `/openapi.json`, `/docs`, `/docs/oauth2-redirect`, and `/redoc` framework routes; the security manifest classifies them too. Do not change the generated inventory by hand.

## Classification of every mounted application route

Rules apply to **each method and path** matching the listed prefix, including path parameters. `Keep` means the capability remains distinct in the unified contract, not that its legacy URL is permanent. `Migrate` means represent it under a canonical v1 resource. `Retire after migration` means the legacy URL stays until every caller moves. All legacy URLs remain reachable with unchanged behaviour. The prefix rows cover the legacy route set; the test in `test_v1_contract.py` checks coverage against the actual app and generated inventory.

## Client demand and v1 resource plan

The bundled Observatory calls `/api/observatory/*`, `/api/continuity/*`, and related log/observability routes from `packages/phlo-observatory/src/phlo_observatory/src/observatory/api/`. `packages/phlo-mcp/src/phlo_mcp/api_client.py` calls the platform, authoring, service, log, and Observatory families noted above. Migrate both before retiring their URLs. The standalone `phlohouse/phlo-observatory` has fixture-backed TanStack `createServerFn` GETs and local-only fake mutations; it is **not** yet a live HTTP consumer. Its typed fixtures mix display strings with domain data. It needs these planned v1 slices, with no endpoints mounted in phase 0:

| Phase | Planned v1 resource families (illustrative paths, not mounted) |
| --- | --- |
| 1 | `/me`, `/environments`, `/services`, `/events` |
| 2 | `/incidents`, `/activity` with durable incident lifecycle and evidence |
| 3 | `/assets`, `/overview`, `/sources`, `/layers` with asset histories and bounded preview |
| 4 | `/jobs`, `/runs`, run-log following and guarded job/run actions |
| 5 | `/catalog`, `/refs`, `/query`, `/saved-queries` with bounded read-only SQL |
| 6 | `/settings`, `/members`, `/service-accounts`, `/audit-events`, `/signatures` |
| 7 | `/branches` with checks, trial merge, and signed merge |
| 8 | `/staging`, `/promotions` with explicit code/config promotion separate from branch merge |

The standalone GET shapes are screen aggregates, not canonical API schemas: duplicate asset list/detail handlers, a fixture query workspace, and a pipeline UI that displays jobs do not justify parallel v1 endpoints. Its incident creation, branch merge, query execution, materialization, schedule toggle, settings save, invitations, and promotion controls have no durable backend yet. Do not advertise them as mounted or successful operations.

## `/api/v1` conventions for implementing phases

- **Authentication and authorisation:** Authenticate every v1 call, including reads and streams, through Phlo's configured user or service principal; do not treat CORS or `PHLO_ENVIRONMENT` as identity. Classify each new route in `security_manifest.py` by canonical action, resource type, and bound path/query/body identity. Check scope and policy before reading sensitive data or acting; 401 for missing identity, 403 for denial, 503 when authorisation cannot be evaluated. The existing manifest still permits optional authorisation in unregulated development for *legacy* paths; v1 routes must enforce their stronger contract explicitly. Bind an audit actor to each mutation. Keep `/health` anonymously accessible.
- **Environment:** Require `?env=prod|staging` on every environment-sensitive v1 operation (including streams and mutations), with no implicit default. The caller cannot submit a Dagster location, Nessie ref, or backend URL. The server resolves the selected value through an operator-configured, explicit allowlist pairing one Dagster code location and one Nessie ref per environment; missing or ambiguous mappings fail with 503, invalid selections with 422. Scope caches, cursors, audit, idempotency, and resource authorisation to the selected environment; never fall back to another environment. `PHLO_ENVIRONMENT` remains a process security/storage mode, never a request selector. Phase 1 owns wiring and cross-environment tests; the phase-0 model validates selection and target shape only.
- **Values and status:** Use UTC ISO 8601 timestamps with offsets, non-negative seconds and counts, and stable machine-readable enums. `healthy`, `degraded`, and `unhealthy` require observed evidence; `unknown` means insufficient evidence and `unavailable` means a required source cannot be queried. Include `observed_at` when available; use `null` for an unobserved metric, never fabricated zero. The representative services model is in `v1_contract.py`. Clients format relative times, units, and display labels.
- **Pagination:** Bounded `limit` (default 100, maximum 500) and opaque `cursor`; return `{items: [...], next_cursor: string|null}` for lists, with stable ordering and a cursor bound to filters and `env`. Reject malformed, stale, or cross-environment cursors with 400; never silently restart at page one. This is stricter than the current offset helper in `pagination.py`, which resets invalid cursors to zero and is not safe for cross-environment v1 pages. Prefer a source-backed cursor or snapshot for changing lists; document consistency on each resource.
- **Errors:** Use `errors.py`'s `{"error":{"code":"...","message":"..."}}` for v1 failures, including validation and authorisation failures, with `x-request-id`. 400 for bad cursor/input, 401/403 for access, 404 for missing authorised resource, 409 for conflicting state or reused idempotency key with different payload, 422 for invalid typed values, 502 for malformed upstream response, and 503 for unavailable dependency/mapping. Never expose backend secrets or render a partial failure as an empty success. Legacy routes currently also emit FastAPI `detail` and flat security errors; normalising those is a v1 implementation task, **not** a change to legacy semantics in phase 0.
- **Events and logs:** Use `text/event-stream` for v1 live events and log follow; authenticate the initial request, scope `env` and target, send typed `event:` and JSON `data:` records, and define a bounded resume cursor (`id:`/`Last-Event-ID`) or explicit resync after a gap. Initial failure uses HTTP error envelope; after headers, send `event: error` with the same envelope and close. Heartbeats do not claim state. Bound retention, connection lifetime, and replay per endpoint. Legacy `/api/loki/runs/{run_id}/stream` remains unchanged: it deduplicates a bounded polling stream and sends `log`, `error`, and `done`, without durable resume IDs.
- **Mutations:** Require a client `Idempotency-Key` for effectful POSTs, scoped to actor, action, target/version, `env`, and request digest; replay the original durable result for an identical key/request, return 409 for conflicting reuse or a stale expected version, and audit attempts and outcomes. PUT/PATCH/DELETE likewise need explicit preconditions, durable result, and audit. A key is not a concurrency guarantee: production multi-replica actions require #989 shared-store operation exclusion or an explicit single-replica restriction. Do not acknowledge an action whose outcome is unknown as success.
- **Signing:** Do not offer signed resolution, role change, merge, or promotion until a real step-up challenge and server-side verification bind actor, meaning, exact action, target, and target version at execution. Reject stale, reused, or mismatched signatures and persist verifiable audit evidence. Existing signature UI or audit records alone do not establish this guarantee or regulatory certification.

**Semantics retained unchanged in phase 0:** all legacy route paths, request/response shapes, authorisation behaviour, `/health` liveness, Loki SSE polling, bounded table preview, narrow legacy query, saved-query storage, guarded retry/cancel and materialisation, continuity plan/apply/verification, settings store, and existing audit facilities. No phase-0 contract model is registered as a route; the v1 rules above take effect only when their owning phases implement and test them.
