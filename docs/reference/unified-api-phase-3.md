# Phase-3 `/api/v1` assets and overview slice

This is a partial backend delivery for [issue #1035, phase 3](https://github.com/phlohouse/phlo/issues/1035). It is not the Observatory UI wiring and does not claim phase-3 acceptance.

Every route requires an authenticated principal, an allow decision from the configured policy backend, and exactly one `env=prod|staging` selector. The server resolves that environment through `PHLO_V1_ENVIRONMENTS`; Dagster assets, checks, and runs are filtered by the mapped repository location before data is returned. The Nessie ref remains operator-controlled and is not accepted from callers. Authorization uses `asset.read` for asset, check, source, layer, and overview reads, and `run.read` for run history. Failures do not become empty asset lists.

## Routes

| Method and path | Evidence returned |
| --- | --- |
| `GET /api/v1/assets?env=...&limit=...&cursor=...` | Dagster asset key, description, compute kind, group, non-materializable source classification, dependencies, and latest materialization timestamp/run ID. When the same key is defined in multiple locations and Dagster history cannot be disambiguated, `history_scoped` is false and history fields are null. Cursor is bounded to `env` and this list; limit is 1–500. |
| `GET /api/v1/assets/{asset_id}?env=...` | Asset definition, Dagster `TableSchemaMetadataEntry` columns, and typed column lineage, when present. `schema_observed_at` is set only when the latest materialization carries schema metadata; static definition metadata has no fabricated observation time. |
| `GET /api/v1/assets/{asset_id}/runs?env=...&limit=...&cursor=...` | Bounded, cursor-paginated Dagster run-feed history filtered to runs whose asset selection contains this exact key and whose run-origin location matches the selected environment. This includes failed and in-progress runs, not only materializations. A cursor is bound to environment and asset ID; each Dagster feed page contains at most the requested 1–500 runs. |
| `GET /api/v1/assets/{asset_id}/checks?env=...&limit=...` | Dagster check definitions scoped by asset key and repository location, plus typed recent evaluation metadata. Each execution's embedded run origin must match the selected environment; runless evaluations are omitted because they lack location identity. Limit is 1–100 per check definition. |
| `POST /api/v1/assets/{asset_id}/audits?env=...` | Accepts only bounded `not_null`, `unique`, and finite ordered `range` declarations, verifies the asset/schema columns, and generates/AST-validates a Pandera source patch. Requires `project:write`, an idempotency key, the single-replica/process gates, and writes an API audit record. Returns a durable `pending_review` proposal; it does not write project code, submit a Git PR, or activate a check. |
| `GET /api/v1/assets/{asset_id}/audits/{proposal_id}?env=...` | Retrieves the persisted proposal source and patch only when asset, environment, and mapped Nessie ref match. Requires `project:write`; unknown or mismatched proposals return not found. |
| `GET /api/v1/tables/{namespace.table}/snapshots?env=...&limit=...` | Ref-bound Iceberg snapshot history from the configured Nessie ref. Identifier syntax is restricted; output is limited to 500 records. |
| `GET /api/v1/tables/{namespace.table}/schema-history?env=...&limit=...` | Ref-bound retained Iceberg schema versions, IDs, field IDs/names/types/requiredness, and current schema ID. Iceberg does not expose observation timestamps through this metadata list, so none are added. |
| `GET /api/v1/assets/{asset_id}/preview?env=...&limit=...` | Runs a read-only Trino preview through a catalog mapped to the exact selected environment/ref. Rows are capped at 100, result pages at 8 MiB, serialized response at 1 MiB, runtime at 20 seconds, planning at 5 seconds, and requested physical scan at 256 MiB. The active Trino `nextUri` is deleted on output overflow, timeout, or client disconnect when available. Duplicate Dagster asset keys across locations are refused. |
| `GET /api/v1/assets/{asset_id}/materialization-estimate?env=...&partition_count=...` | Validates that the asset exists in the selected Dagster location and returns the requested partition count. Cost, scanned bytes, and duration are explicitly `null` with unavailable status fields because no estimate source exists; this is not a workload estimate. |
| `POST /api/v1/assets/{asset_id}/materialize?env=...` | Guarded Dagster materialization request. Defaults to dry-run, requires an idempotency key, pins the mapped repository location/name and Nessie ref tag, and appends API operation audit evidence. Live launch requires the single-replica and ref-tag-contract operator gates. |
| `POST /api/v1/assets/{asset_id}/backfill?env=...` | Guarded Dagster backfill with explicit caller keys (1–500), one latest key, or Dagster-native `allPartitions`. Latest uses `partitionKeyConnection(limit: 1, ascending: false)` and means the last key in Dagster's partition-definition ordering, not a universal timestamp promise. Full uses the native selector without enumerating keys. Both require an asset-associated job and a partition set whose resolved job/location/repository match; the location-scoped selector receives asset, job, environment, selection, and Nessie-ref tags. The request is dry-run by default and retains idempotency, audit, and live-action gates. |
| `GET /api/v1/sources?env=...&limit=...&cursor=...` | The same asset records filtered by Dagster `isMaterializable == false`, before pagination. This is the Dagster source/non-materializable classification. |
| `GET /api/v1/layers?env=...&limit=...&cursor=...` | Counts and latest materialization grouped by Dagster's real `groupName`; it does not assert that Dagster groups are governance/data layers. |
| `GET /api/v1/overview?env=...` | Asset and materialized-asset counts, latest materialization timestamp, phase-2 incident counts, SLA-backed freshness counts, and Dagster run status counts from up to 100 recent runs filtered by the configured location. `quality_checks` reports passing/total latest evaluations and failing asset IDs from at most 50 assets, 100 definitions, and 101 execution records per check; it is explicitly `unknown` with null counts and failing asset IDs on source failure or an exceeded bound. Runless and cross-location evaluations are excluded. `run_history_truncated` signals a full 100-row result. |

Asset definitions, materialization evidence, and column-lineage metadata come from Dagster GraphQL. Snapshot/schema history loads Iceberg metadata using the operator-mapped Nessie ref. Incident counts and explicit freshness SLA overrides come from the phase-2 durable incident store. Dagster outages, malformed responses, and incident-store outages fail the overview instead of returning synthetic zeroes.

## Configuration and limits

- Preview is **fail-closed** unless all operator settings are present: `PHLO_V1_PREVIEW_SERVER_LIMITS_CONFIGURED=1`, `PHLO_V1_PREVIEW_TRINO_USER` and secret `PHLO_V1_PREVIEW_TRINO_PASSWORD` for a dedicated authenticated read-only Trino identity, HTTPS `TRINO_URL`, and `PHLO_V1_PREVIEW_CATALOGS` as JSON mapping exactly `prod` and `staging` to distinct catalog names and their exact `nessie_ref`. The API sends Basic authentication on query, poll, and cancellation requests. Each Trino catalog must be pre-provisioned with the intended Nessie REST ref. The server must enforce authentication, a read-only access policy, a resource-group/concurrency ceiling for that identity, and permit only the bounded query session properties used by the API. A boolean alone does not prove that cluster policy; the operator must verify the Trino configuration before setting it. API admission is two queries per process, so the Trino resource group is also required for a global cap across replicas.
- Trino's query physical-scan budget is an operational limit on bytes Trino accounts as scanned, not a strict ceiling on object-store traffic or manifest-planning bytes. The API refuses caller SQL, pins catalog in `X-Trino-Catalog`, selects only the mapped relation, and uses typed identifier quoting. It does not use PyIceberg row-limited scans or the legacy Trino preview route.
- Live asset actions fail closed unless `PHLO_V1_ACTIONS_SINGLE_REPLICA=1`, `PHLO_V1_ACTIONS_SINGLE_PROCESS=1`, and `PHLO_V1_ACTIONS_REF_TAG_CONTRACT=1` are set after deployment verification. These are operator assertions: deploy one API replica with one worker process, keep its `.phlo/state` idempotency journal and `.phlo/audit` log on the project-owned persistent volume, and ensure the mapped Dagster locations honor the `environment` and `phlo/ref` run tags. The code never auto-enables these gates.

## Not implemented; source boundary

- **Partition selection limits:** latest and full actions are implemented through bounded Dagster mechanisms. Latest returns one key by Dagster's descending partition ordering (which may not mean a timestamp for static/custom definitions). Full delegates completeness to native `LaunchBackfillParams.allPartitions`, scoped to the prevalidated partition set, repository, and code location; it intentionally does not report a partition count because none is enumerated. Live actions remain gated and were not invoked.
- **Executable audit/check creation:** POST validates a constrained declarative request against the selected asset schema and persists a generated, AST-validated Pandera source patch in the project-scoped durable Observatory state. The proposal is `pending_review` and retrievable from the matching asset/environment/ref; this local review artifact is not an actual customer Git branch or PR, and the API never writes the mounted project code. The source-control publish step still needs an operator-designated customer repository/base branch and project-scoped Git App permissions/reviewer policy. The maintenance-only `phlo-github-writer` is not used. A human must approve and merge the code, after which the customer code-location deployment/reload must discover the `AssetCheckSpec`/Pandera decorator. No check is active before that. The overview's passing/total/failing-asset fields are data-quality evidence from environment-scoped Dagster checks, not compliance audit-log events; the phase-6 compliance audit log is separate.
- **Usage evidence:** no environment/ref-scoped usage authority has been wired; cost, bytes, and duration estimates remain explicitly unavailable.
- **Schema/snapshot history:** implemented through ref-bound Iceberg metadata. Iceberg snapshots and retained schema metadata are not Dagster audit/check outcomes and are reported separately.
- **Phase-3 UI:** Observatory client wiring remains separate.

No migration or shared/production write is part of this change.
