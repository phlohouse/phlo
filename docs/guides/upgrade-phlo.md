# Upgrade Phlo

Phlo has separate commands for package changes, generated service files, project configuration, data migrations, and source codemods. `phlo services upgrade` reconciles generated files only. The guarded `phlo operations upgrade` command proves one fixture transition and does not upgrade a live deployment.

## Supported boundary

The only accepted pair is `0.14.0` to `0.15.0`. This pair is an immutable fixture policy used to test the continuity journey; it is not a declaration that a real `0.14.0` deployment can be upgraded in place. Every other pair fails before mutation. Current package version `0.16.2` does not add another supported pair.

The boundary is defined in [`phlo.operations.upgrade`](../../src/phlo/operations/upgrade.py) and tested in the [upgrade contract](../../tests/operations/test_upgrade_contract.py).

## Prepare the package set

1. Record the installed package set and retain the current lock file.

   ```bash
   uv pip freeze > phlo-packages.before.txt
   cp uv.lock uv.lock.before
   ```

2. Change the Phlo package constraints in `pyproject.toml` as one reviewed set. The root extras define the intended bundles: `defaults` contains the supported default stack, `core-services` contains the service core, and `runtime` contains runtime libraries. `observe` and `openmetadata` are opt-in. Do not derive support from installability; check [`registry/support/v1.json`](../../registry/support/v1.json).

3. Resolve and install through the project's normal locked workflow.

   ```bash
   uv lock
   uv sync --locked
   ```

Keep `uv.lock.before`, the old environment or images, and the pre-upgrade data backup until all verification passes. Updating one Phlo package independently can leave entry points, service images, and provider contracts on different versions.

## Review generated-stack changes

Pause writers and verify provider data backups before any storage migration. Do not use `services init --force` to upgrade an existing project.

```bash
phlo services upgrade --dry-run --output upgrade-plan.json
```

Inspect `upgrade-plan.json` privately. It contains the exact candidate file contents, source and installed distribution versions, old and candidate images, input hashes, conflicts, new companions, and dependency restart order. The console omits candidate contents because project replacements can contain credentials. Do not commit the plan or backups.

Fresh generation records `.phlo/upgrade-baseline.json`. A file changes automatically only if it still matches that baseline, is absent, or already matches the candidate. Directly edited or unknown generated files conflict. Move custom Trino or Dagster configuration into the declared `phlo.yaml` service-file overrides, or reconcile it manually before replanning. Personal Compose layers, credentials, named storage volumes, and unrelated provider files remain in place. The command does not delete obsolete files or run Git commands.

For projects generated before baseline recording, supply a pristine project generated by the previous release with the same configuration:

```bash
phlo services upgrade --previous-generated /private/previous-project \
  --dry-run --output upgrade-plan.json
```

Do not point this option at the customised live project. An unavailable previous baseline leaves differences as conflicts rather than authorising replacement. Keep the same `--previous-generated` and `--production` options for plan and apply.

If the plan reports a MinIO image migration, use the existing provider command:

```bash
phlo minio migrate-image
# After a verified object backup and writer pause:
phlo minio migrate-image --apply
```

Verify existing object reads and credentials, then generate a new upgrade plan. Other storage-image changes require a provider-supported migration and data validation before replanning. Container health alone does not prove storage-format compatibility.

After reviewing the concrete plan, apply with its printed token:

```bash
phlo services upgrade --apply upgrade-plan.json --confirm <plan-token>
```

Apply refuses changed inputs, changed templates, storage migration blockers, and conflicts. It resolves candidate Compose with the installed container backend and existing personal layers before mutation. It saves private originals and file modes under `.phlo/upgrade-backups/<plan-token>/` before replacing files. Repeating a successful apply checks the saved receipt and current inputs and outputs, then returns without changing files. On platforms without POSIX private-file guarantees, apply and private plan output refuse unless you explicitly pass `--allow-insecure`; this option does not claim Windows ACL protection.

Inspect the resolved Compose configuration before restarting in the reported dependency order. Complete the provider's data checks and the installed-consumer Observatory acceptance journey before discarding backups.

### Check durable API schema separately

Generated-file apply does not inspect a database or authorise schema changes. Releases that introduce configurable environments delegate the incident/query constraint migration to the installed API package:

```bash
python -m phlo_api.migrations --check --json
```

This command uses `PHLO_RUN_EVIDENCE_DB_URL`, checks in a read-only transaction, and reports `004_configurable_environments` as `compatible` (exit 0) or `required` (exit 1). A connection failure is not compatibility. If required, stop writers, verify a database backup, obtain `services.migrate` authorisation, and follow the installed API migration instructions before running `--apply --backup-confirmed --json`. Do not pass backup confirmation merely because generated-file originals exist: they are not a database backup. No startup `ALTER`, automatic database migration, or compatibility inference from container liveness occurs in `services upgrade`.

### Recover generated files

An ordinary replacement failure restores the original files and modes. Keep the failure report and private backup directory. No containers or data migrations run inside this transaction.

After a process crash, do not remove `.phlo/upgrade.lock` and retry blindly. Compare the saved `plan.json` with current files. Restore each replaced file from the matching relative path in the backup, restore its mode from `original-modes.json`, and remove only files recorded as newly created. Restore the saved `.phlo/upgrade-baseline.json` too, or remove it if the original mode record is null. Do not copy the backup tree over the project wholesale. After confirming recovery and that no upgrade process is running, remove the empty lock directory and create a new plan. These steps recover generated files only, not provider data.

## Installed Observatory acceptance: incomplete

The exact-BOM runner now requires `observatory_installed_journeys` for both artifact and deployment evidence. The driver is a work in progress, not a qualification result. Missing candidate or previous BOMs, unavailable tooling, legacy environment activation, private-mount access failures, and unverified preview enforcement must fail acceptance. Source tests, synthetic driver pages, and the operations fixture cannot replace this demonstration.

The runner accepts a separate immutable previous release BOM:

```bash
python scripts/release_golden_path.py \
  --candidate-bom /private/candidate/bom.json \
  --previous-candidate-bom /private/previous/bom.json \
  --evidence-output /private/results/evidence.json
```

Use only disposable resources and approved artifacts. This command is not a publication, deployment or manual qualification-dispatch authorisation. It reuses existing BOM validation, isolated wheel installation and image-digest pinning. It adds no publication trust mechanism and executes no release workflow dispatch.

The driver generates the previous project through its real `services init --profile api --no-dev` contract, not a nonexistent previous `--observatory-dev` flag. Legacy installations without a resolvable environment binding currently stop: the compatibility/activation seam must be completed before claiming a retained-volume journey. Storage migrations remain provider-owned; a required API schema migration also stops for the installed migration procedure rather than silently altering the database.

The intended journey checks real typed data, 251 Nessie namespace commits, legacy and correctly scoped Dagster records, all six UI routes, asynchronous branch detail, cursor progression, public read-query results, denial, readiness and outage/restart recovery. Query assertions compare the complete two-row dataset without assuming ordered first-N behaviour. API credentials mount only `api-secrets/`; server keys remain in separate provider-owned mounts. The driver probes file readability using the exact images and fails on UID mismatch. It neither broadens permissions nor sets deployment security assertions from generated-file existence. Live process/replica/bounds verification is still unfinished.

Screenshots remain beside the evidence output. Failure retains the private temporary project and backup for investigation; do not upload that directory because it contains credentials. Successful synthetic tests prove the driver's checks only. No exact candidate/previous artifact pair has been exercised for this implementation, and Windows and live installed-browser acceptance remain unverified.

## Migrate project configuration

Preview the current configuration migration:

```bash
phlo config upgrade --plan-only
```

`phlo config upgrade` has one step: add the default `infrastructure` section to `phlo.yaml`. If that section exists, the command refuses unless `--force` replaces it. The command validates a temporary candidate and atomically replaces `phlo.yaml` only after validation.

```bash
cp phlo.yaml phlo.yaml.before
phlo config upgrade
phlo config validate
```

Review before using `--force`; it discards the existing infrastructure section.

## Migrate data and code

Data migration specifications are independent of the deployment fixture command. Validate and dry-run each reviewed spec before authorising a write:

```bash
phlo migrate list
phlo migrate validate <migration.yaml>
phlo migrate run <migration.yaml> --dry-run
phlo migrate run <migration.yaml>
phlo migrate status
```

The dated decorator codemod reports changes by default. Gate or inspect it, then write:

```bash
phlo migrate decorators-2026-05 . --check
phlo migrate decorators-2026-05 . --diff
phlo migrate decorators-2026-05 . --write
```

The write forms require mutation authorisation. The migration CLI contract is in [`migrate.py`](../../src/phlo/cli/commands/migrate.py).

## Exercise the fixture upgrade contract

This procedure applies only to the supported fixture pair.

1. Create and verify a backup whose manifest records Phlo `0.14.0`.

   ```bash
   phlo operations backup create --target <new-empty-backup-root>
   phlo operations backup verify --backup-set <backup-set-directory>
   ```

2. Create a plan and save its JSON output. The target must be new or empty.

   ```bash
   phlo operations upgrade plan \
     --from 0.14.0 --to 0.15.0 \
     --backup-set <backup-set-directory> \
     --target <new-empty-fixture-target> \
     --format json > upgrade-plan.json
   ```

3. Configure `PHLO_OPERATIONS_JOURNAL_DIR`, obtain mutation authorisation, then apply with the token from the plan.

   ```bash
   phlo operations upgrade apply \
     --plan upgrade-plan.json \
     --confirmation-token <plan-token> \
     --fixture-substrate \
     --format json
   ```

Apply writes version markers beneath the fixture target in this order: `postgres.schema`, `nessie.catalog`, `iceberg.metadata`, then `minio.policy`. It does not change packages, containers, schemas, catalogues, object-store policy, or a running service.

## Verify and choose recovery action

Require all of these before discarding the old package set or backup:

- `uv sync --locked` completes from the committed lock;
- `phlo config validate` succeeds;
- applicable migration dry-runs and tests pass;
- `phlo services status` reports the selected services healthy after a real package deployment;
- the fixture result has `state: succeeded`, `accepted: true`, and successful reconciliation for all four steps.

`postgres.schema` is the last declared rollback-safe step. A failure in that step returns `rollback_action: restore`. Once `nessie.catalog` starts, the contract does not claim rollback safety; failures return bounded `forward_repair` details. If reconciliation throws after submissions, the result is `unknown`, automatic replay is blocked, and an operator must reconcile manually.

For a real package rollout, the rollback-safe point is before data or provider migrations begin: retain the old lock/images and a verified backup, and verify that backup while the old package set can still run. The current CLI cannot restore a live deployment, so do not call the fixture `rollback_action` an operational rollback plan.
